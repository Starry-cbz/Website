## 新安装与共享市场

v1.1 以全新安装为主要交付方式，使用交易协议 `5`、数据库结构版本 `2`、物品快照格式 `2`。取得对应发行构件后：

1. 按游戏版本与 JVM 选择一份运行 JAR，使用独立服务器及插件数据目录。
2. 单服使用新 SQLite 文件；共享市场准备独立、空的 MySQL/MariaDB 数据库。保留原目录与数据库，不为新安装清空已有市场。
3. 首次启动生成配置后正常停服，填写自己的许可证、网络、节点和经济配置，再启动检查。产品 ID、授权端点和可信公钥保留发行默认值。

新安装默认使用插件目录中的持久 SQLite 文件，适合一个市场节点。多服务器共享市场使用 MySQL/MariaDB，不能让多个游戏节点并发写同一个 SQLite 文件。已有数据库连接不会因新增默认值被换成空库。

备份 SQLite 时先正常停服或使用一致备份方式；运行中的 WAL 数据库不能只复制 `.db` 文件。

每个节点保留唯一 `network.node-id`；同一市场的网络身份、游戏版本、物品配置和币种身份必须一致。数据库连接失败会显示不可用，不创建另一个市场冒充原数据。

## 已有 v1.0 市场

v1.1 不承诺直接换包或无缝升级。先完整备份原数据库、插件目录、原 JAR、玩家／世界及经济插件数据，在独立副本核对迁移、资产及恢复流程，再决定是否切换原环境。

v1.1 构件保留旧结构检查、迁移前备份、旧节点围栏和资产恢复保护；这些机制不能代替完整旧环境的实际验证。不要混跑新旧构件、删除数据库、改写币种身份或用新安装配置覆盖旧市场。保留原备份和操作证据，按[迁移与回滚说明](/kitemarket/operations#v1-0-to-v1-1)处理。

## 界面与集成范围

基础插件提供完整原版 GUI。开发者可通过配置与公开 Java SDK 制作自己的 ItemsAdder 界面；界面沿用服务端的真实物品、受保护动作、权限和交易确认。

ItemsAdder、Oraxen、Nexo、MMOItems 的物品身份桥接读取真实公共 API。可用桥接和声明式规则不会放宽物品保真，支持范围应以实际 API 与验证记录为准。

## 计分板、NPC 与权限插件

可选集成提供显示与入口，具体构件支持仍以验证记录为准。未安装或 API 不兼容时只停用对应集成，基础市场可独立使用。

| 集成 | 用法 |
| --- | --- |
| PlaceholderAPI | `%kitemarket_state%`、`%kitemarket_network_id%`；钱包使用 `%kitemarket_wallet_coins_available%`、`%kitemarket_wallet_coins_frozen%`，将 `coins` 替换为实际币种 ID |
| Citizens | 将真实 NPC ID 写入 `integrations.citizens.npc-ids`，正常重启后右键打开 `/km` |
| LuckPerms | `%kitemarket_luckperms_primary_group%` 读取已加载玩家的主组；交易仍检查有效 Bukkit 权限 |

钱包占位符使用短时缓存；未就绪、过期或查询失败返回空值，不显示假零。显示值不用于扣款或判断交易成功，NPC 入口也不会绕过权限和确认。

## 只开放需要的交易模式

`market.enabled-types` 默认包含 `BUY`、`SELL` 和 `AUCTION`。例如只开放竞拍：

```yaml
market:
  enabled-types: [AUCTION]
```

首页、发布、命令和 SDK 使用同一限制。可配置任意非空子集；未知类型或空列表会被拒绝。重载后的新交易按新设置执行，已有订单仍可撤回、到期结算和领取，已冻结的竞拍资金不会因为关闭竞拍而被遗留。

## 结果不明确时

充值、提现、领取、批量上架与管理操作都有各自结果。页面成功提示不能替代另一笔操作的成功；批量中有成功项也不等于整批完成。

遇到 `UNKNOWN`，保留原操作并查看[核对步骤](/kitemarket/operations#核对-unknown)。当前余额或背包截图不足以单独证明历史外部副作用；不要重复扣款、补发或把未知当成失败。风险分数和云端建议也不能确认交易结果。
